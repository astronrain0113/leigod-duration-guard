> 起因：`docs/真机发现-关闭保护架构问题.md`。真机实测推翻了关闭保护的两条旧前提。
> 状态：**机制已在本机以「结构仿真靶机」完成闭环验证（94 项全通过）；
> 真机闭环尚未执行**——不得视为已交付。

## 一、为什么必须重构（三条实测事实）

| # | 事实 | 证据 |
| --- | --- | --- |
| 1 | 真实雷神窗口**整片客户区**对 `WM_NCHITTEST` 一律返回 `HTCLIENT(1)` | `tests/out/real_close_caps_admin.txt`：176 个采样点无一例外，连 ✕ 中心也是 1 |
| 2 | 点 ✕ **不关窗、也不走 `SC_CLOSE`**，而是弹出应用内确认框（「最小化到托盘」/「真的退出」） | 用户真人实测反馈，见 P0 文档 §2.3 |
| 3 | 窗口 `GetWindowRect == GetClientRect`（零非客户区），标题栏（`≡ — ✕`）全为应用自绘 | 同上探针的 `rect/frame/client` 三项完全相同 |

由此：

- 旧判据 `WM_NCHITTEST == HTCLOSE` 在真机**恒为假** → 关闭意图**永远不会**被识别；
- 旧机制 `EnableMenuItem(SC_CLOSE, MF_GRAYED)` 对 ✕ **前提不成立**（✕ 根本不走那条路）；
- 旧结论依据「点 ✕ 后窗口是否消失」判断成败 → 在真机上**必然误报**
  （✕ 本来就只弹框、不关窗）。第一次 `real_close_test.py` 的 `verdict="拦截生效"` 就是这样来的。

**结论：不注入 DLL / 不打补丁的前提下，唯一能实现「点 ✕ 时先确保暂停才放行」的位置，
是输入层（系统回调本进程的低层鼠标钩子）。** 这符合规格书 §四（不注入、不 Patch）。

## 二、分层设计

```
用户点 ✕
   │
   ├─ 层级1  悬停预暂停（可选，默认关）  WH_MOUSE_LL / WM_MOUSEMOVE
   │          光标在 ✕ 邻域停留 ≥300ms 且雷神在前台 → 提前暂停，把等待降到 0
   │
   ├─ 层级2  【主路径】吞点 → 确保暂停 → 重放        WH_MOUSE_LL / WM_LBUTTONDOWN
   │          ① 命中 ✕ 热区 → return 1（系统不再把这次点击派发给任何窗口）
   │          ② 消费端跨进程核查：WindowFromPoint 的根窗口必须仍是雷神
   │          ③ 取当前状态：PAUSED → 直接重放；RUNNING → 跑暂停流程；UNKNOWN → 不放行
   │          ④ 只有「重新检测到 PAUSED」才重放这次点击 → 雷神自己的确认框正常出现
   │
   ├─ 层级3  确认框监测（待真机确认形态后实现）       SetWinEventHook
   │          雷神 pid 出现新的顶层窗口（或页内确认层）→ 确保 PAUSED
   │          兜住层级2 被绕过的情形（触摸/远程桌面/托盘菜单退出）
   │
   └─ 层级4  系统关闭路径兜底（保留旧机制）          EnableMenuItem(SC_CLOSE, MF_GRAYED)
              对 ✕ 无效（已实测）；覆盖 Alt+F4、任务栏右键「关闭窗口」
```

### 2.1 判据：为什么不能只看几何

规格书 §十三 明确反对「鼠标位置 == 右上角」这种单点判断。`should_swallow()` 采用
**四条联合条件 + 消费端一条跨进程核查**，缺一不可：

| # | 条件 | 位置 | 作用 |
| --- | --- | --- | --- |
| 1 | 保护已开启 且 不处于「用户显式放行」 | 钩子（快照） | 尊重用户的逃生选择 |
| 2 | 当前状态 **不是 `PAUSED`** | 钩子（快照） | 已暂停就完全不干预，把误吞概率压到最低 |
| 3 | 该点落在雷神窗口矩形内 | 钩子（快照） | 排除屏幕其他位置的点击 |
| 4 | 该点落在 **✕ 热区**（相对窗口宽高的比例） | 钩子（快照） | 缩小到标题栏右上角 |
| 5 | `WindowFromPoint` 的根窗口 **必须是雷神** | 消费端（跨进程） | 防止「窗口被遮挡但坐标恰好落在矩形内」的误吞 |

第 5 条只能在消费端做：钩子回调里做跨进程 `SendMessage`/`WindowFromPoint` 会拖慢回调，
超过系统 `LowLevelHooksTimeout`（约 300ms）后 **Windows 会静默摘掉钩子**——保护直接失效，
且不产生任何错误。核查不通过时立即**重放**这次点击，用户几乎无感。

### 2.2 ✕ 热区：用相对比例，来自实测

真机实测（Leigod v11.3.2.9，窗口 1500×938，DPI 120）：✕ 中心 `(2003,318)`，
即距右边 27px、距顶边 18px → 归一化中心 `(0.982, 0.019)`，半宽/半高 `0.020 / 0.024`。

```
热区 = 以窗口 (0.982, 0.019) 为中心、半宽 max(18px, w×0.020) × 半高 max(18px, h×0.024) 的矩形
```
反算验证：对 1500×938 的窗口得到中心 `(2001,320)`，与实测 `(2003,318)` 偏差 ≤4px；
窗口移动/缩放后仍命中（用例 `t_close_intent` 用「右移 400px + 放大 1.5 倍」验证）。
**绝不保存绝对屏幕坐标。**

### 2.3 悬停预暂停为什么默认关闭

它比吞点更激进：**会真的把加速停掉**。若只看矩形几何，用户在别的程序里移动光标、
恰好掠过「雷神所在屏幕区域的右上角」，就会平白打断加速。因此叠加三重防护：

1. 必须 `GetForegroundWindow() == 雷神`（雷神不在前台，光标就是「路过」）；
2. 必须在邻域**停留** `prepause_dwell_ms`（默认 300ms），快速划过不触发；
3. 消费端再核查一次光标是否仍真的在雷神身上。

即便如此仍有一个真实副作用：用户在雷神前台把光标挪到右上角歇一下，也会暂停加速。
因此**默认关闭**，作为「更快的放行」选项由用户按需开启。
主路径（吞点→暂停→重放）已完全满足规格书 §十四，不依赖它。

### 2.4 Fail Safe 与「离手保护」的取舍

- **不放行才是默认**：暂停未确认为 `PAUSED` 时**绝不重放**那次点击，
  用户会看到「点了 ✕ 没反应」，同时收到托盘通知要求手动暂停。
  这严格对应 §十四情况3/4 与 §十六（点击成功 ≠ 暂停成功）。
- **死手开关（`swallow_deadman_ms`，默认 2500ms）**：消费端每轮刷新一个截止时间；
  若消费端卡死或崩溃，超过截止时间后钩子**自动停止吞点**。
  这是刻意的「局部 fail-open」：一直吞点而无人处理，用户会连雷神都关不掉，
  比偶尔漏拦一次更糟。触发时会发出 `degraded` 事件告知用户。
- 因此 **`ui.refresh_ms` 必须显著小于 `swallow_deadman_ms`**，
  否则死手会周期性过期、吞点时灵时不灵。默认 500ms vs 2500ms，余量充足。

### 2.5 硬前提：必须提权

雷神 PE 清单是 `requireAdministrator`，恒以高完整性级别运行。非提权进程的低层钩子
无法拦截发往高完整性窗口的输入（UIPI）；对提权窗口调用 `EnableMenuItem` 也会被静默拒绝
（探针实测：未提权返回 `0xFFFFFFFF`，提权返回 `0x00000000`）。

→ 未提权时本程序**明确上报**「输入层关闭保护无效」，绝不假装可用。

## 三、代码结构

| 文件 | 职责 |
| --- | --- |
| `leigod/close_intent.py` | **判定层（纯逻辑、可单测）**：`GuardSnapshot` 快照、热区几何、`should_swallow` / `should_prepause`。刻意不依赖任何系统调用 |
| `leigod/close_protection.py` | `CloseIntentWatcher`（可吞点的低层钩子，回调内只做快照读取 + 数值比较）、`CloseIntentGuard`（消费端：核查 → 暂停 → 重放）、`CloseProtection`（旧机制，降级为系统关闭路径兜底） |
| `leigod/confirm_dialog.py` | **层级 3（确认框监测）**：`SetWinEventHook` 通路 + OCR 通路。**OCR 扫描跑在独立线程**，`poll()` 只是 O(1) 取结果——见 §六 |
| `leigod/duration_detector.py` | 新增 `button_rect_on_screen(state)` / `button_center_on_screen(state)`：用 OCR 文字框**现算**暂停按钮屏幕矩形（真机 UIA 枚举 0 控件时的唯一可用定位手段） |
| `leigod/duration_controller.py` | 暂停策略回退链：UIA → 已校准相对坐标 → **OCR 实时定位**；三级都不可用则如实失败，绝不猜坐标 |
| `detection/coordinate_fallback.py` | 新增 `send_left_click(x, y, marker)`：用 `dwExtraInfo` 标记重放的输入，避免钩子吞掉自己发的点击形成死循环 |
| `core/protection_engine.py` | 接线：启动/绑定/每轮 `maintain()`/关闭保护时释放；`_guard_ensure_paused()` 复用规格书 §十 的暂停流程 |

## 六、消费端 tick 的硬契约（本层最容易被破坏的地方）

引擎主循环的一轮 tick 同时承担三件**不可被拖慢**的事：① 消费「点了 ✕」的关闭意图；
② 刷新输入层死手的武装窗口；③ 维持界面刷新节拍。任何一件被慢操作阻塞，都会引发
**静默**的功能退化——不报错、不告警，只是「保护忽然不生效了」。

层级 3 接线时就踩出了这一类缺陷（详见 README §13.2 的四条根因）：

| 契约 | 内容 | 违反后的表现 |
| --- | --- | --- |
| **tick 内不得有耗时不可控的同步操作** | 整窗 OCR（300ms~1.3s）必须移到工作线程；`ConfirmWatch.poll()` 只做 O(1) 取结果 | 关闭意图在队列里等到过期 → **点了 ✕ 毫无反应** |
| **关闭意图的消费必须排在慢步骤之前** | `_tick()` 中 `_consume_close_intents()` 先于 `_poll_state()` | 同上（意图「白白等过一次 OCR」） |
| **新鲜度阈值必须相对实测节拍自适应** | `_intent_max_age()` = `clamp(2×实测消费间隔 + 0.3s, 1500ms, 5000ms)` | 阈值卡在临界点（1.5s vs 1.4s tick）→ 间歇性失灵 |
| **死手窗口必须按实测节拍放宽、但保留上限** | `_arm_window()` = `clamp(tick_ewma × 3, 2500ms, 10000ms)` | 固定窗口被「忙」而非「死」顶穿 → ✕ 周期性恢复可点 |

四项观测均已暴露到状态里（`input_layer.arm_ms/tick_ms/deadman_ms`、
`close_intent.accepted/expired/missed/max_age_ms`、`confirm_layer.ocr_thread`），
并各自配了回归用例。**判据**：`close_intent.expired` 持续增长即等于「点了 ✕ 没反应」。
