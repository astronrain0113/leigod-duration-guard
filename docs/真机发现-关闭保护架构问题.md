## 一、结论摘要

关闭保护（规格书 §十二 / §十四，本项目的**第一核心功能**）依赖两条链路。
**已提权复验**（消除 UIPI 混淆）+ **真人点 ✕ 实测**后的结论：

| 链路 | 依赖 | 真机结论 | 状态 |
| --- | --- | --- | --- |
| **意图识别**：`WM_NCHITTEST == HTCLOSE` | 用户点的 ✕ 是**系统的**关闭按钮 | 窗口内 176 个采样点**全部**返回 `HTCLIENT(1)`；连按系统度量算出的 ✕ 中心也是 `1`；`SendMessageTimeout` 返回 1（**消息已送达，非被拦**） | 🔴 **已确认不成立** |
| **拦截**：`EnableMenuItem(SC_CLOSE, MF_GRAYED)` | ✕ 走 `WM_SYSCOMMAND/SC_CLOSE` 通路 | 提权后调用返回 `0x00000000`（成功）、`GetMenuState` 变 `0x20000001`（`MF_GRAYED` 生效）——**系统层机制可用**；但真人点 ✕ 后**窗口根本没有关闭**（走的是应用内自绘确认框），`SC_CLOSE` 通路**在 ✕ 上压根没被走到** | 🔴 **对 ✕ 无效（前提不成立）** |

以及**第三条、也是本次最重要的实测事实**：

| 观察 | 结论 |
| --- | --- |
| 真人点击自绘 ✕ 后，雷神**没有关闭**，而是弹出自己的小框询问「最小化到托盘」/「真的退出」 | ✕ 由**渲染进程**处理，**不触发任何窗口级关闭消息**；真正的关闭动作后移到弹框的「真的退出」按钮上 |

**两条链路此前只对靶机 `LeigodMockWnd`（普通带系统菜单的 Win32 窗口）验证过**，
而靶机与真实客户端（Electron + 自绘标题栏 + 应用内确认框）在窗口结构上**本质不同**。因此
`tests/probe_close_protection.py` 得出的「方案 1 有效」结论**不能外推到真机**——
这正是一次**测试有效性的失败**：靶机结构与真机不一致，自动化全绿但真机静默失效。

三个**已可下结论**的推论：

1. **意图识别必须重写**。整窗客户区一律 `HTCLIENT`，说明标题栏（含 ✕）是应用自绘、
   由渲染进程处理点击。`close_protection.is_close_button_at()` 依赖 `HTCLOSE`，
   在真机上**恒为假** → **关闭意图永远不会被识别**，连"尝试暂停"的机会都没有。
   - 判据必须换成**联合条件**：相对几何（✕ 热区）+ 窗口身份一致 + 点击落在雷神 `rect` 内
     + 窗口在前台 + 当前状态非 `PAUSED`（§十三 禁止把单点几何当唯一依据）。
2. **`SC_CLOSE` 拦截路径与 ✕ 无关**。✕ 既不关窗、也不走 `SC_CLOSE`。
   继续把它当作"关闭保护的主力"是错的；它只能降级为**系统关闭路径的兜底**
   （`Alt+F4`、任务栏右键「关闭窗口」）。
3. **真正的关闭风险点需要重新定位**。关闭保护必须覆盖的是
   **「应用内确认框里的『真的退出』」** 与 **托盘菜单退出**，
   而不是 ✕ 本身（✕ 只负责弹框）。

风险性质：这是**静默失效**——面板/日志可能显示「保护已开启」，但用户点 ✕ 时
雷神照常走自己的流程，暂停流程根本来不及执行。这正是本项目要防止的场景。

## 二、证据（事实，可复核）

真机窗口（`tests/out/real_close_caps_admin.txt`）：

```
主窗口   : HWND=0x20076E  title='雷神加速器'  class=Chrome_WidgetWin_1  pid=23660
进程     : leigod.exe  D:\LeiGod_Acc\leigod.exe  v11.3.2.9
rect     : (530, 300, 2030, 1238)   尺寸=1500x938   DPI=120
frame    : (530, 300, 2030, 1238)
client   : (530, 300, 2030, 1238)      ← 与 rect/frame 完全相同
style    : 0x14C20000
           = WS_VISIBLE | WS_CLIPSIBLINGS | WS_CAPTION | WS_BORDER
             | WS_DLGFRAME | WS_MINIMIZEBOX
           → 无 WS_SYSMENU、无 WS_THICKFRAME、无 WS_MAXIMIZEBOX
```

1. **窗口没有任何非客户区**：`GetWindowRect == GetClientRect`。这说明标题栏
   （含右上角 `≡ — ✕`）是**应用自绘**的，不是系统标题栏。
2. **`WS_SYSMENU` 未设置**：`0x14C20000 & 0x00080000 == 0`。
3. **没有最大化按钮**（与无 `WS_MAXIMIZEBOX` 一致）：真机截图里只有
   `≡`（紫色，属应用菜单）、`—`、`✕` 三个自绘字形（`ThunderGuard/logs/frames/topbar_zoom.png`）。
4. **UIA 枚举到 0 个控件**：`ui_automation.control_count = 0`
   （`real_inspector/inspector.json`）——Electron 无障碍树未暴露，
   故 §七「第一优先级 UIA」在真机上不可用，只剩 OCR（用于**读**，不能**点**）。
5. `GetSystemMenu(window, FALSE)` 返回**非 NULL 句柄**（`0x1150909`，含 7 个菜单项）
   —— 尽管 `WS_SYSMENU` 未设置，系统菜单句柄依然存在。

### 2.2 提权复验（消除 UIPI 混淆，2026-09-29 10:11）

完整输出：`tests/out/real_close_caps_admin.txt`（其中 `本进程提权 : 是`）。

- **`WM_NCHITTEST` 全窗返回 `HTCLIENT(1)`**：176 个采样点（dy 4~46，dx −420~0）
  **无一例外**都是 `1`；连按系统度量算出的 ✕ 中心 `(2003,318)` 也是 `1`。
- **消息确实送达**：`SendMessageTimeoutW(WM_NCHITTEST)` 返回 `1`、结果值 `1`
  （非被拦），因此 `1` 是**窗口自身的真实回答**，不是 UIPI 造成的空值。
- **`EnableMenuItem` 提权后成功**：返回 `0x00000000`（成功），`GetMenuState`
  由 `0x20000000` → `0x20000001`（`MF_GRAYED` 生效）；探针随后**已还原**为 `0x20000000`。
- **落点即渲染子窗口**：✕ 区域 `WindowFromPoint` 落在
  `Chrome_RenderWidgetHostHWND`（0x1608A2），即该处点击由 **Chromium 渲染进程**接收。

> 对照未提权运行（`real_close_caps_user.txt`）：`WM_NCHITTEST` 全返回 `0`、
> `EnableMenuItem` 返回 `0xFFFFFFFF`。两组对比**证实**了 UIPI 的存在，
> 也证实「未提权结论不可用」。**雷神恒为管理员运行 → 本程序必须提权。**

### 2.3 自绘 ✕ 的真实行为（真人实测，2026-09-29）

**这是本次最重要的一条事实，它推翻了此前所有关于「拦截 ✕」的假设。**

用户如实反馈：

> 「点了 ✕，但是你并未拦截，因为软件本身会再弹出一个小框询问你是要
>   最小化到托盘还是真的退出。」

即：**点 ✕ 不会关闭雷神窗口**，而是触发了雷神自己的**应用内确认框**。

由此产生三个必须写进设计的结论：

1. **第一次 `real_close_test.py` 的 `survived=true` 是假象**。窗口没关，
   不是因为 `MF_GRAYED` 拦住了 `SC_CLOSE`，而是因为**✕ 本来就只弹框、不关窗**。
   该次运行的 `verdict="拦截生效"` **作废**（首版测试的硬伤是"只看窗口是否消失"，
   没有点击证据；即便后来补了点击证据，判据本身仍然是错的——**窗口存活 ≠ 拦截成功**）。
2. **`SC_CLOSE` 通路在 ✕ 上从未被走到**。✕ 的点击由 Chromium 渲染进程接收
   （`WindowFromPoint` 落在 `Chrome_RenderWidgetHostHWND`），
   走的是前端事件 → 应用内部逻辑，与 `WM_SYSCOMMAND/SC_CLOSE` 无关。
   → 「禁用系统菜单项」对 ✕ **天然无效**，不是"可能无效"，而是**前提不成立**。
3. **真正的关闭风险点后移**：危险动作是确认框里的 **「真的退出」**，
   其次是**托盘菜单退出**。关闭保护的价值重心必须从"拦住 ✕"改为
   **"在『真的退出』真正执行之前确保已暂停"**。

### 2.4 由此暴露的测试有效性缺陷（必须修）

| 项 | 靶机 `mock_leigod.py` | 真实雷神 | 影响 |
| --- | --- | --- | --- |
| 窗口样式 | `0x00CF0000`（含 `WS_SYSMENU`） | `0x14C20000`（**无** `WS_SYSMENU`） | 靶机有系统标题栏，真机没有 |
| ✕ 归属 | 系统自绘，`WM_NCHITTEST` 返回 `HTCLOSE(20)` | 应用自绘，全窗返回 `HTCLIENT(1)` | **意图识别在靶机通过、在真机恒假** |
| 点 ✕ 的后果 | 直接 `WM_CLOSE` → `DestroyWindow` | **弹应用内确认框**，不关窗 | 判据「窗口是否消失」在真机失效 |
| 确认框 | 无 | 「最小化到托盘」/「真的退出」 | 关闭保护完全未覆盖 |

→ 结论：**必须新增「结构仿真靶机 v2」**（`tests/mock_leigod_chrome.py`），
复刻上表右侧的结构与行为，否则任何关闭保护的自动化验证都只是自欺。

## 三、结论（已提权复验）

1. **【已确认】关闭意图识别在真机上不成立**（此结论不受 UIPI 影响）。
   整个客户区一律 `HTCLIENT`，说明标题栏（含 ✕）由应用自绘、点击交给渲染进程。
   → `is_close_button_at()`（依赖 `HTCLOSE`）**恒为假**，关闭意图**永远不会被识别**。
   - 替代判据：**窗口矩形相对几何**（如「相对右上角 `(w−Δ, Δ)` 邻域」）
     + 联合条件（窗口身份一致 / 点击落在雷神 `rect` 内 / 当前状态非 `PAUSED` / 窗口在前台）。
   - 注意 §十三 明确反对把「鼠标位置 == 右上角」当**唯一**依据，故必须联合判定。
2. **【已确认】`SC_CLOSE` 在提权后确实可禁、可复原**（系统层机制有效）。
3. **【已确认，真人实测】自绘 ✕ 不走 `SC_CLOSE` 通路，且不直接关窗。**
   点 ✕ 弹出应用内确认框（「最小化到托盘」/「真的退出」），
   → `MF_GRAYED` 对 ✕ **无效**（前提不成立，而非"可能无效"）。
   → 关闭保护的主力机制必须改为**输入层拦截 + 状态前置**，
   `SC_CLOSE` 仅保留为**系统关闭路径的兜底**（`Alt+F4` / 任务栏右键关闭）。
4. **【已确认】真正的关闭风险在确认框的「真的退出」与托盘菜单退出。**
   保护必须在这些动作真正执行前确保「已重新检测到 `PAUSED`」。

> 纪律（规格书 §三十三）：关闭保护在真机**不得**标记为已验收，
> 直至新方案（见 `docs/关闭保护-设计方案v2.md`）在真机上完成
> 「点 ✕ → 自动暂停 → 放行 → 确认框出现」的闭环验证。

## 四、影响

- **关闭意图识别已确认失效**：用户点 ✕ 时 `is_close_button_at()` 恒假 →
  保护流程永远不会被触发。这是「静默失效」，因为面板此时可能仍显示「保护已开启」。
- **`SC_CLOSE` 拦截对 ✕ 无效（前提不成立）**：✕ 由渲染进程处理、只弹应用内确认框，
  与系统菜单无关。规格书 §十二「点 ✕ 时先确保暂停才放行」在真机上
  **按原设计完全不成立** → 测试 A/B/C/D（§三十五）无法按原方式通过。
- **判据「窗口是否消失」在真机上失效**：点 ✕ 后窗口**本来就不消失**，
  因此「窗口存活」**不能**作为拦截成功的证据（第一次 `real_close_test.py` 正是在此翻车）。
- Fail-safe 语义不受影响：`UNKNOWN`/`RUNNING` 仍不会被当作 `PAUSED`，
  也不会「无法确认就放行」——只是**拦不住**，并且**来不及暂停**。
- 暂停控制（§十）另有一条已知限制：真机 UIA 不可用/时有时无，暂停必须走
  **相对坐标点击**，而坐标点击要求本程序提权（否则 UIPI 丢弃合成输入）。
  因此 `duration.coordinate.ratio` 必须先在真机校准。

## 五、候选替代方案（均不注入、不打补丁，符合 §四）

> 已按 §2.3 的新事实修订：**保护目标从「拦住 ✕」改为「在『真的退出』执行前确保已暂停」**。
> 完整设计见 `docs/关闭保护-设计方案v2.md`，此处只列取舍。

| 方案 | 思路 | 优点 | 风险 / 未知 |
| --- | --- | --- | --- |
| A. 输入层吞点击 | `WH_MOUSE_LL` 回调命中 ✕ 热区时 `return 1` **吞掉该次点击**（系统不再派发给任何窗口），随后走暂停流程；**确认 `PAUSED` 后重放该次点击**，让雷神自己的确认框正常出现 | 严格满足 §十四「先确保暂停才放行」；不依赖系统菜单 | 必须是提权进程（低完整性钩子无法吞掉发往高完整性窗口的输入）；几何判定需多重条件防误吞；重放需用 `dwExtraInfo` 标记避免自吞 |
| B. 前置暂停（hover 预警） | 光标进入 ✕ 邻域且 `RUNNING` 时**提前**暂停 | 不吞点击、副作用最小；用户几乎无感 | 存在「点得比暂停快」的竞态；需去抖与提示 |
| C. A + B（**推荐**） | B 作常态（无感），A 作保底（竞态/暂停失败时仍拦住） | 兼顾体验与严格性 | 复杂度最高，需分别验证两条路径 |
| D. 系统关闭兜底（`SC_CLOSE`） | 保留 `EnableMenuItem(MF_GRAYED)` | 覆盖 `Alt+F4` / 任务栏右键「关闭窗口」 | 对 ✕ **无效**（已实测）；提权后才生效 |
| E. 确认框监测 | `SetWinEventHook` 监听雷神 pid 的新顶层窗口；出现「退出确认框」即确保 `PAUSED` | 兜住 D 与 A 都被绕过的情况；覆盖托盘菜单退出路径 | 若确认框是 Electron 页内绘制（非独立 HWND），则需退化为截图 + OCR 检测 |
| F. 注入子类化窗口过程 | 替换目标窗口的 `WndProc` 以否决 `WM_CLOSE` | 最彻底 | **违反 §四（DLL/进程注入）→ 不采用** |

> §十三 明确反对「鼠标位置 == 右上角」这种简单判断。方案 A/B 的几何判定
> 必须与「窗口身份一致 / 点击落在雷神 rect 内 / 窗口在前台 / 当前状态非 PAUSED」
> **联合**成立，并在真机做误吞验证，不能只靠单点几何。
