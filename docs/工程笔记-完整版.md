# 雷神加速器总时长保护工具（Leigod Duration Guard）

一个与雷神加速器 Windows 客户端**高度绑定的总时长保护伴生工具**。

它的核心任务只有一个：**防止用户在停止游戏、关闭雷神或忘记操作时，让雷神的总时长继续无意义消耗。**

它是一根"保险丝"，不是自动点击脚本、不是游戏辅助、更不是雷神 API 客户端。

---

## 1. 它保护什么

雷神客户端存在这样的场景：用户已经停止加速、甚至直接关闭了游戏，但"总时长"仍处于运行状态；用户直接关掉雷神或忘记点"暂停时长"，于是总时长被白白消耗。

本工具在两处设防：

| 层级 | 机制 | 说明 |
| --- | --- | --- |
| **第一保险丝** | **关闭保护** | 用户点雷神的 ✕ 时，先确保总时长已暂停，才允许关闭；无法确认就**不允许关闭** |
| **第二保险丝** | **游戏退出自动暂停** | 所有被监控的游戏都退出并等待 N 秒（默认 30）后仍未重新启动，则自动暂停总时长 |
| **退出保护** | **退出本程序前先确认已暂停** | 从托盘/面板退出本程序时，若雷神仍在计时（或无法确认），先尝试暂停，确认后才退出；确认不了就把选择权交回用户，并且**不会静默退出** |

> 游戏监控**不能**代替关闭保护：游戏可能崩溃、用户可能只是暂时退出、用户可能直接关闭雷神。因此两者独立存在，默认都已启用。
>
> 退出保护解决的是最后一道口子：本程序自己退出时若不管，用户会以为"我已经收拾干净了"，而计时器其实还在跑——那正是本程序要防的事。

---

## 2. 设计原则（不可妥协的几条）

1. **不使用雷神 API。** 不调用官方/非官方接口，不依赖 `account_token`、Cookie 或账户密码，不通过网络请求模拟客户端操作，不建立任何账户登录系统。全项目**零网络调用**。
2. **尽可能不修改雷神本体。** 不替换 `leigod.exe`、不改 DLL/资源/安装包/ASAR、不做 DLL 注入或进程注入、不 Patch 二进制。全部功能通过 HWND、Windows 窗口消息、UI Automation、OCR、窗口截图与相对窗口坐标实现。
   > 关闭保护 v2 使用**低层鼠标钩子**（`WH_MOUSE_LL`）拦截 ✕ 点击。这**不是**进程注入：它由 Windows 在**本进程内**回调，不往雷神进程写任何代码或数据，也不改变其内存与二进制；且遵循「不跨进程调用、超时自动卸手」的纪律（见 §10）。
3. **Fail Safe，不是 Fail Open。** 无法确认"已经暂停"时，一律**阻止关闭**，而不是默认放行。宁可雷神暂时关不了，也不能让用户在不知情下损失几个小时总时长。
4. **UNKNOWN 绝不等于 PAUSED。** 任何无法证明"已暂停"的情况都是 UNKNOWN，而 UNKNOWN 一律按"不安全"处理。
5. **点击成功 ≠ 暂停成功。** 只有重新识别到「开启时长」，才允许说"暂停成功"。
6. **不保存绝对屏幕坐标。** 只保存相对雷神窗口的 `ratio` / `pos`，以便移动窗口、换显示器、改分辨率、DPI 125%/150% 时重算。

## 3. 状态模型

| 状态 | 判定依据 | 含义 | 允许关闭雷神？ |
| --- | --- | --- | --- |
| `RUNNING` | 存在「暂停时长」按钮（红色） | 总时长正在消耗 | ❌ 先暂停 |
| `PAUSED` | 存在「开启时长」按钮（白色） | 总时长已暂停 | ✅ 允许 |
| `UNKNOWN` | 窗口不存在 / UI 未加载完 / UIA 找不到控件 / OCR 无法识别 / 文字矛盾 / 颜色不可靠 / 页面切换中 / 点击后无变化 / 版本变化 / 任何无法证明已暂停的情况 | 未知 | ❌ **禁止** |

识别按三级优先级：**① UI Automation（能 Invoke 就直接 Invoke）→ ② 窗口内相对区域坐标 → ③ 顶栏区域 OCR + 图像特征**。三路证据冲突时结论为 UNKNOWN，不强行猜测。

### 4.1 从源码运行

```bat

:: 环境自检（找不到雷神时会以退出码 2 结束，属正常）
python main.py --check

:: 普通启动（先开雷神也行，随后开本程序也行）
python main.py

:: 启动器模式：先启动雷神、等主窗口出现、绑定、进入保护
python main.py --launcher

:: 只驻留托盘
python main.py --minimized
```

### 4.2 使用打包好的 exe

```bat
:: 图形版（不弹控制台）
dist\LeigodGuard\LeigodGuard.exe

:: 图形版 + 启动器模式
dist\LeigodGuard\LeigodGuard.exe --launcher

:: 控制台工具版（界面诊断 / 坐标校准要用它，因为图形版没有控制台可看）
dist\LeigodGuard\LeigodGuardCUI.exe --check
dist\LeigodGuard\LeigodGuardCUI.exe --inspector
dist\LeigodGuard\LeigodGuardCUI.exe --calibrate --mode auto
```

> **配置与日志写在 exe 旁边**（`config\config.json`、`logs\`），所以请把整个 `dist\LeigodGuard` 目录复制到**有写权限**的位置（例如 `D:\Tools\LeigodGuard`），不要放在 `Program Files` 下。
>
> **启动时会弹一次 UAC**：exe 清单已声明 `requireAdministrator`，这是必须的——雷神本身强制要求管理员权限，本程序不提权则关闭保护会静默失效（详见 §10 已知限制第 1 条）。请点「是」放行。`LeigodGuardCUI.exe` 同样会弹 UAC，因为诊断与校准也要与高完整性的雷神窗口交互。

### 4.3 体积与响应速度（2026-09-29 两轮优化，含真机反馈驱动）

| 项 | 优化前 | 优化后 | 做法 |
| --- | --- | --- | --- |
| 产物体积 | 610.9 MB | **242.0 MB** | ① 工具版 exe 与图形版同目录、**共用一份 `_internal`**（省 305.9 MB；早先放进 `cui\` 等于把依赖复制两遍）；② 排除从未加载的大件：`opencv_videoio_ffmpeg`、Qt 的 `opengl32sw`、`Qt6Quick`、PIL 的 `_avif`（再省 69 MB） |
| 状态刷新间隔 | 2000 ms | **1000 ms** | `duration.poll_ms` 默认下调 |
| 单轮识别耗时 | 1.3 s 以上 | **数十毫秒** | `detection.ocr_mode=auto`：UIA 已给出确定结论时**跳过整窗 OCR**；每 60s 强制刷一次，保证按钮定位几何不过期 |
| **点 ✕ 后自动暂停的等待** | **数秒~20 秒级** | **约 1 秒级** | ① `ocr_mode` 改为**识别器实例默认档**（旧写法只在状态轮询那条路上传了参数，暂停链路的 4~8 次 `detect()` 全吃默认值 `always`，每次白跑 1.3s 整窗 OCR —— 见下方「第二轮」）；② 验证改**两段式**：先 UIA 快轮询（0.1s/次、不跑 OCR），UIA 给不出结论才上 OCR 兜底；③ 关闭保护把**刚读到的状态**传给暂停流程，不再重读；④ `ensure_visible` 不再无条件抢前台并白等 200ms |
| 面板贴边 | 左右横跳 | **钉住不乱跑** | 默认 `ui.pin_side=True`：选定一侧后**永不自动换边**，只跟雷神平移；想换边点面板「⇄ 换到另一侧」 |
| 拖动跟手 | 滞后半秒后归位 | 约 10 Hz 跟进 | 新增**独立几何快跟定时器**（`ui.follow_fast_ms`，默认 100ms）：只读一次 `GetWindowRect` 就挪面板，不查进程、不做识别 |
| 面板背景 | **71% 像素透明** | 完全不透明 | 见下方「第二轮」第 2 条 |

> `auto` 只在「UIA 内部一致且非 UNKNOWN」时跳过 OCR —— UIA 认不出或自相矛盾时照旧跑，
> **省时间不以牺牲判定可靠性为代价**。排障时想每轮都跑：把 `detection.ocr_mode` 改成 `always`。

#### 第二轮（2026-09-29 深夜，用户真机反馈驱动）

用户原话：「**点第一次 ✕ 的时候等待他自动帮我暂停时长的时间有点长了**；这个软件 ui 背景是透明的
我有点看不到字；**吸附程度还是太差了，可以固定在加速器一角吗，哪怕我拖动加速器工具也不会乱跑**」。
三条都是真实缺陷，逐条定位到根因后才动手：

1. **暂停延迟 —— 性能开关只接了一条路。**
   上一轮加的 `ocr_mode="auto"` **只传给了状态轮询**（`protection_engine._poll_state`）；
   `duration_controller` 里 `pause()` 的 before、`_verify()` 的每一轮、重试前的复检，
   共 4~8 次 `detect()` 全都走函数默认值 `"always"` —— 每次白跑一遍 1.3s+ 的整窗 OCR。
   修复的核心不是「再调几个参数」，而是**把档位放到识别器实例上作为默认值**
   （`DurationDetector.default_ocr_mode`），让所有调用点（含诊断与验证脚本）自动生效。
   **教训：性能开关不能靠调用方记得传，默认值才是唯一可靠的地方。**
   另加两段式验证、状态复用、去掉无条件的 200ms 前台等待。

2. **背景透明 —— 样式表写在了不生效的元素上。**
   抓图实测：面板 **71% 的像素 alpha=0**，连正中心都是透明的（用户「看不到字」完全属实）。
   根因是 QSS 只写在 `QWidget#panel` 上，而 Qt 对**顶层普通 QWidget** 的样式表背景在
   `WA_TranslucentBackground` 下不绘制。改为**外层透明窗口负责圆角 + 内层 `QFrame#card`
   承载不透明底**，并加了像素级回归（断言全透明像素 < 15%、空白处 alpha=255 且是浅色）。

3. **吸附乱跑 —— 两件事被绑在一起了。**
   一是**位置跟随和状态刷新共用了节拍**：面板位置跟着 `duration.poll_ms`（1000ms）走，
   拖雷神时就是「窗口走了、面板还在原地，半秒后啪地归位」。位置跟随另有独立定时器（100ms）。
   二是**换边判据会在雷神靠近屏幕边缘时把面板甩到对面**：拖动过程中看就是面板在两个位置之间跳。
   默认改为**钉住当前一侧**，只跟雷神平移、越界则夹到屏幕边缘；换边由用户显式点
   「⇄ 换到另一侧」决定，并写回配置记住选择。钉住拿掉了系统的自动行为，就必须配套给一个手动出口。

### 4.4 开机待命：开雷神时自动唤起（2026-09-29 新增）

用户要的是「**当我想用雷神加速器时，这个工具会自动出现**」。这件事由
**待命守望**（`launcher/watch.py` + `ui/standby.py`）实现：一个只做守望的
极轻常驻进程，不加载 OCR、不建面板，每 2 秒只看两件事 ——
**雷神在不在**、**守卫在不在**；雷神在而守卫不在，立刻把守卫以**可见面板**拉起。

| 文件 | 作用 |
| --- | --- |
| `开机待命-开启.bat` | 建计划任务（每次登录自动待命）**并立刻在当前会话启动一次** |
| `立刻待命.bat` | 只启动待命，不动任何开机设置 |
| `开机待命-关闭.bat` | 删除计划任务（正在跑的待命需右键托盘图标 →「退出待命」） |

三个必须知道的事实（都是真机踩出来的，不是推测）：

1. **计划任务的 `onlogon` 触发器只在「下次登录」时才触发**，不会回溯当前已登录的会话。
   实测证据：任务 `StartBoundary=23:30`，23:34 复查 `logs/guard.log` 仍停在 23:29:42
   —— 任务从未触发过。所以 `开机待命-开启.bat` 在建完任务后**额外执行一次
   `schtasks /run`**，让你当场就能用上，不必重启。
2. **旧「待命」= 完整守卫 `--minimized` 是不成立的**：守卫会在雷神退出时正常退出
   （这是规格要求的跟随行为），而旧方案**没有任何机制把它拉回来**，
   于是下一次开雷神时工具不在。守望进程与守卫是分开的，守卫退了它还在。
3. **`--minimized` 的表现和「没启动」几乎一样**：只有一个托盘图标，
   还常被 Windows 收进溢出区。所以待命进程有自己的托盘图标（蓝色小方块 + 右下角状态色小点），
   启动和唤起时各弹一次气泡，把「我做了什么」说出来（§三十三）。

**唤起一次之后会「去武装」**，直到雷神彻底退出过一次才重新武装 ——
否则你在雷神运行期间手动关闭守卫，它会立刻被拉回来，等于你关不掉它。
那是替用户做决定，不做。

### 4.4.1 状态读不出来？先按「重新检测状态」（2026-09-30 新增）

面板与托盘菜单都有一项「**重新检测状态**」。它做三件事：
① 重新定位雷神主窗口（**绑错了能纠正**）；② 强制**全量识别**（`ocr_mode=always`，
这一次不省 OCR，要的就是一个确定答案）；③ **如实说明结论与原因** ——
读不出来就明说读不出来，并列出常见成因（被挡住 / 没加载完 / 正弹着确认框），
不猜、不含糊。

> 为什么要给用户这个按钮：状态读不出来的成因有四五种，程序**不能替用户猜**是哪一种。
> 给一个「你说不清就按一下」的入口，比让用户重启程序友好，也比分不清成因就乱猜要诚实。

#### 它背后的那次真实事故（值得记住）

用户报「工具又无法判断时长状态了，昨晚还好好的」。查日志得到的是一条完整的因果链：

```
13:06:15  雷神启动
13:06:17  守望发现 leigod.exe 进程 → 立刻唤起守卫        ← 太早了
13:06:17  守卫绑定窗口 HWND=0x20918 class=Chrome_WidgetWin_0 尺寸=1920x1130
13:06:19  [confirm_dialog] 出现新的顶层窗口：Chrome_WidgetWin_1  ← 真主窗口 2 秒后才建好
          → UIA 只枚举到 6 个控件（正常 ~476）、OCR 报「雷神不在前台」
          → 状态永久 UNKNOWN、关闭保护恒 BLOCK_UNKNOWN
```

根因是两条叠加，**都不是「识别算法」的问题**：

1. **`find_main_window` 会在类名/标题都没命中时静默退化成「挑最大的顶层窗口」**，
   于是绑到了 Electron 的辅助顶层窗口（`Chrome_WidgetWin_0`，比真主窗口还大），
   而且**绑上之后再也不复核** —— 只能重启程序。
2. **守望只要看到进程就唤起守卫**，而雷神启动途中「辅助窗口已可见、主窗口未建好」
   有一个约 2 秒的窗口期，正好被撞上。

修复（三层，各自都有回归用例）：

| 层 | 改动 | 效果 |
| --- | --- | --- |
| 窗口定位 | 新增 `LeigodWindow.match`（`class`/`title`/`nofilter`/`fallback`）与 `find_main_window(strict=)` | **匹配方式不再被隐藏**；严格模式下没认准就返回 `None`（宁可等，也不绑错） |
| 引擎绑定 | 严格优先 + 最多等 `leigod.strict_bind_wait_seconds`（默认 15s）；弱匹配**持续复核并自动改绑** | 绑错不再是终局；等够了才退而求其次，且**弹窗如实告知** |
| 守望 | 新增纯函数 `should_treat_present()`：以「认得出的主窗口」为准，只看到进程时给 20s 宽限 | 从源头不让守卫在雷神启动途中被叫起来；超时仍认不出也会唤起，**不会变成永不保护** |

### 4.4.2 【严重】打包版 OCR 一直是坏的（2026-09-30 修复）

**症状**：用户报「工具又无法判断时长状态了」。查到守卫日志里
`ui_automation=UNKNOWN(窗口内未找到目标按钮（共枚举 5 个控件）)` ——
雷神窗口不在前台时，Chromium 的无障碍树会塌缩（正常 ~476 个控件），
UIA 这条主路**整条失效**，此时唯一还能读状态的就是 OCR。

而 OCR 在打包版里**从来没成功过**：整份历史日志里 `ocr=UNKNOWN(未识别到可用文字)`
一直存在，只因为 UIA 一直好用而被掩盖。

**证据链（三步，缺一步都会误判）**：

| 步 | 做了什么 | 结果 |
| --- | --- | --- |
| 1 | `LeigodGuardCUI.exe --inspector` 抓现场 | 截图**有效**（PrintWindow，1500x938，mean=77），裁剪区里「开启时长」清清楚楚，但 `ocr.lines = []` |
| 2 | 把同一张 `duration_region.png` 丢给**源码环境**的 RapidOCR | 识别出 **8 行**，含「开启时长」→ 判定 `PAUSED` |
| 3 | 数 `dist/**/_internal` 里的 `.onnx` | **0 个**（3 个模型 + 4 个 config.yaml 全都没打进去） |

**两处根因（缺一不可，第一处修完才暴露出第二处）**：

1. **数据文件没收**：`spec` 里 `datas=[]`，而 `hiddenimports` 只把**代码**打进 PYZ；
   RapidOCR 的 3 个 `.onnx` 模型与 4 个 `config.yaml` 是**数据文件**。
   → `RapidOCR()` 构造时找不到模型、抛异常被 `except` 吞掉 → 此后每轮 OCR 静默返回空。
2. **子模块没收**：RapidOCR 是**按 YAML 动态 import** 子模块的
   （`ch_ppocr_v3_det.text_detect` / `ch_ppocr_v3_rec.text_recognize` / `ch_ppocr_v2_cls.text_cls`），
   PyInstaller 的静态分析看不到。只补数据文件后，运行期报
   `AttributeError: module 'ch_ppocr_v3_det' has no attribute 'TextDetector'`。

**修复**：两个 spec 都加上 `collect_data_files()` + `collect_submodules()`；
并给一条**独立回归**盯住两半（否则这个坑会安静地复发）。

**顺带做的第二件事：让失败可见。** 旧 `ocr.engine_available()` **只检查能否 import**，
模型全丢时照样报「可用」—— 一个会把人带偏的假信号（本次排查就被它误导过一轮）。
现在它要求「引擎真的能构造起来」，并把失败原因留在 `ocr.last_error()`，
可由 `--check`、识别证据（`ocr=UNKNOWN(OCR 引擎不可用：…)`）、
以及引擎启动时的 WARNING 三处看到。

**修复后实测（同一台机器、同一个窗口状态）**：

```
UIA 控件数   : 5            ← 主路仍然失效（雷神不在前台）
OCR 识别行数 : 9            ← 「开启时长」等，conf 0.53~0.85
→ 最终状态   : PAUSED       ← 状态恢复可读
守卫日志      : STATE_CHANGED → PAUSED（ui_automation=UNKNOWN(…); ocr=PAUSED(…)）
```

### 4.4.3 延迟与体积治理（2026-09-30 第三轮，用户要求「点 ✕ 后 1~2 秒」）

#### ① 延迟：量化到毫秒，A/B 在同一台真机上测

用户报「点第一次 ✕ 等待自动暂停的时间有点长」。从守卫日志量出的实际耗时是
**8.5 / 7.8 / 6.3 / 5.8 秒**。根因不在识别算法，而在**每轮识别都为整棵控件树的
每个节点读 9 个属性**（真机 474 个控件 → 每轮约 4000 次跨进程 COM 调用）。

`tests/measure_uia_scan.py`（提权运行）在**同一个窗口**上做 A/B：

| 做法 | 单次耗时 | 说明 |
| --- | --- | --- |
| A 旧：每个控件都建 `ControlInfo`（8 属性 + GetPattern） | **2184.7 ms** | 旧 `find_duration_controls` 的真实成本 |
| B 新：只读 `Name`，**命中的才**建对象 | **821.2 ms** | 全量扫描（每 3 秒一次，用于纠偏） |
| C 新：走控件缓存，只重读 1~2 个控件的 `Name` | **0.3 ms** | 稳态轮询 / 暂停后复核的成本 |

修复后「确保暂停」的路径变为：缓存快读（≈0）→ UIA Invoke → 快相轮询（≈0）
→ **一次全量扫描做地面真相复核**（≈0.8s）。预计 1 秒量级。

> **为什么快路径不自己下结论**：缓存元素万一还在返回旧名字（COM 代理被缓存），
> 快路径就会给出过期结论。所以 `_verify` 里连续两次快相 PAUSED 之后**必须做一次
> 全量扫描复核**——快路径只负责"等得少"，**下结论必须用地面真相**。
> 这条写在代码注释里，也有回归用例盯着。

同时修掉一个同源的隐性故障：引擎 tick 被这几秒的枚举堵住时，
**死手窗口无人刷新** → 日志里反复出现
`[degraded] 消费端超时未刷新，已自动停止吞点`，而那正是用户点 ✕ 的时刻 ——
第二次点就吞不住了。延迟降下来，这个窗口也就消失了。

#### ② 后台占用

| 项 | 改动 | 依据 |
| --- | --- | --- |
| 状态轮询 | 自适应：RUNNING 原速 / UNKNOWN ×1.4 / PAUSED ×2（`duration.adaptive_poll`）；基准 `duration.poll_ms` = 500 | 风险不对称：PAUSED 时唯一能变成 RUNNING 的途径是用户自己在雷神里点的，晚一点知道毫无风险 |
| 面板跟随 | 位置跟随由独立的 150ms 定时器负责，兜底周期 500ms → 1000ms | 位置与状态是两个节拍，不该共用 |
| 守望轮询 | 2000ms → 3000ms | 每次都要进程枚举 + 窗口枚举，没必要为"立刻"白烧 CPU |
| OCR 自检 | 移到后台线程 | 构造引擎要 1~2 秒 + 几十 MB，不该阻塞第一次状态识别 |

#### ③ 体积：263.3 → 241.7 MB（实交付口径）

`_internal` 的构成（精简前实测）：`cv2.pyd` **82.3 MB**、PySide6 59.4 MB、
onnxruntime 35.8 MB、numpy 26.3 MB、rapidocr 模型 13.1 MB、PIL 5.3 MB。

> 口径说明：交付目录 = 图形版 exe + 控制台版 exe + `_internal` + config/logs + bat。
> 只算图形版目录（不含控制台版 exe，6.6 MB）是 235.3 MB；上面写的是**实际交付目录**的 241.7 MB。

本轮砍掉的是**逐项确认过程序不会加载**的 Qt 组件（累计 −21.6 MB）：
Qt 翻译 `.qm`（96 个，6.4 MB，本程序界面全中文硬编码不做国际化）、`Qt6Pdf`（4.4）、
`Qt6OpenGL`（1.9，QWidgets 走 raster）、`Qt6Network`（2.6，不联网）、
`Qt6VirtualKeyboard`（0.4）、图像格式插件（1.8）、`qdirect2d`（1.0）、TLS 后端（0.6）。

> **做不到 <200 MB 的原因（如实说明）**：剩下的大头是 **OpenCV 82 MB**，
> 而它是 RapidOCR 的依赖（实测它用到 **25 个 cv2 API**，含 `findContours` /
> `minAreaRect` / `warpPerspective`），我们自己的源码里**一处 `cv2` 都没有**。
> 要再往下走只有两条路，都需要单独决策：
> 1. **换 OCR 后端**（例如 Windows 内置 `Windows.Media.Ocr`，可降到 ~130 MB）——
>    代价是依赖系统 OCR 语言包、跨机器一致性变差，且本机当前**无网络**无法安装依赖；
> 2. **自己用 numpy 实现 PP-OCR 的检测/识别后处理**（约 25 个 cv2 API）——
>    工作量大，且一旦语义有偏差会**静默**降低识别准确率，风险远大于收益。
>
> 在"识别可靠性 > 体积"的取舍下，本轮先停在 241.6 MB。

#### ④ 真机复测：一次点 ✕ 的耗时拆解（2026-09-30 19:45，build .8）

用户在真机上点了一次 ✕，日志留了痕：

```
19:45:36.496  暂停流程开始：当前状态=RUNNING（ui_automation=…；无 ocr 证据 = OCR 被正确跳过）
19:45:37.050  UIA 调用按钮「暂停时长」成功          ← +554ms：这一次 Invoke 本身
19:45:39.028  暂停成功：第 1 次点击后确认已暂停      ← +1978ms：确认环节
19:45:39.029  确保暂停耗时 2535ms（其中 UIA 扫描 683ms）
```

**2535ms 里，全量扫描跑了 3 次**（各 ~683ms）：读初值一次、点击后重扫一次、
最后"地面真相复核"一次。而**第三次是多余的** —— 它复核的那一读本来就是一次真实的全量枚举。
修复：`detect_uia` 现在把"这一读来自缓存还是全量枚举"如实标出来（`from_cache`），
`_verify` 据此判断：**来自全量枚举的 PAUSED 直接采纳**（它就是地面真相）；
只有连续两次**缓存**结论才需要再复核一次。省掉一次扫描 ≈ 683ms。

> 保守一点说：这次改的是"少做一次多余的复核"，**没有放松任何判据** ——
> 发布 ✕ 点击前仍然必须有一次真实的全量枚举作为证据。

#### ⑤ 启动期那次 `[degraded]` —— 我改错过一次，被测试抓住

同一份日志里 `19:40:59` 出现 `[degraded] 消费端超时未刷新，已自动停止吞点`。
原因是启动后的**首轮 tick** 要等 Chromium 建好无障碍树 + 构造 OCR 引擎（实测 10s 量级），
把 2.5s 的死手窗口顶穿了 —— 偏偏落在"刚启动、用户最可能点 ✕"的时段。

我第一次的修法是把窗口初值直接给到上限（10s）。**`test_close_guard.case_deadman` 当场抓住**：
那条用例验证的是"消费端从未运行 → 钩子必须尽快放手，否则用户被自己锁死"。
初值给 10s 会让**真正死掉的消费端**也吞 10 秒点击。

最终改法：宽限必须是**显式的、由引擎主动申请的、有时限的**
（`CloseIntentGuard.set_startup_grace()`，引擎在 `start()` 里申请 15s）。
其余场景一律按配置值走。默认**没有**宽限 —— 这条也有回归用例盯着。

> 这条记录的是一类容易犯的错：**为了让某个场景好过，把全局默认值改宽**。
> 全局默认值会被所有场景共享，而其中一定有场景需要它保持严格。

#### ⑥ 一条运维提醒（我踩过）

跑那 8 套自动化验收时，**先把桌面正在运行的守卫停掉**。
守卫每轮都要扫一次真机控件树（~683ms），会抢 CPU，导致
`test_e2e_mock` 这类**条件轮询**用例出现假失败（实测 3 项假失败，停掉守卫后全绿）。

### 4.4.4 界面视觉重构（2026-10-01，用户要求「让 UI 高级一点」）

功能稳定后专做视觉。原则是：**美观不是加装饰，而是让信息的主次一眼可辨**。

#### 设计系统（`ui/theme.py`）

旧版把颜色与字号写死在样式表串里，于是「标题 13px、按钮 11px、提示 10px」散落各处，
改一处就与别处不一致。现在所有视觉决策只在 `theme.py` 定义一次：

| 维度 | 规则 |
| --- | --- |
| 字阶 | 只允许 **10 / 11 / 12 / 13 / 17** 五档 |
| 间距 | 只用 **4 的倍数**（4/6/8/10/12/14），纵向节奏一致 |
| 圆角 | 卡片 14 · 控件 9 · 药丸全圆 |
| 颜色 | **中性阶**（底/线/字）+ **语义色**（三态 + 强调色），语义色只允许从 token 取 |

配色语义（功能选择，不是审美选择）：RUNNING=红（要避免）、PAUSED=绿（安全）、
UNKNOWN=琥珀（既不当安全也不当危险，一律按不安全处理）；
另加一个**中性态 IDLE** 给「保护中/待命」这类**与时长状态无关**的药丸 ——
没有它的时候只能借三态色，结果「保护中」被画成绿色，而绿色在这一套界面里专指
「时长已暂停」，用户会读错。

#### 版面重排：每一块回答一个不同的问题

| 位置 | 回答的问题 |
| --- | --- |
| 品牌标记 + 标题 | 这是哪个程序 |
| 右上药丸（保护中/未生效/保护已关/待命） | **关闭保护起没起作用** |
| 状态主卡片（大字 + 大白话 + 「N 秒前确认」） | **时长在不在被消耗** |
| 盾牌行（颜色随"是否真的锁住"） | 上次关闭是怎么被处理的 |
| 主按钮 / 两个兜底按钮 / 底部工具行 | 我能做什么 |

两处刻意的改动值得记下来：

1. **药丸换轴**。原先右上角药丸也显示时长状态，于是「已暂停」在同一屏出现两次；
   更糟的是让人以为「保护生效」与「时长状态」是同一件事。现在药丸只说保护，
   主卡片只说时长。
2. **信息降噪**。`HWND 0x1607d2 · 1080×700 · 120dpi` 这类内容从界面挪进悬停提示；
   界面只留「雷神窗口 1500×938」。通用解释行（`lbl_hint`）不再占版面，
   内容并入 tooltip —— 它和主卡片那句大白话本来就在说同一件事。

#### 自绘控件（`ui/widgets.py`，零外部资源）

程序要单文件分发，多带图标目录就多一处「可能找不到」的风险（本项目已在 DLL/模型
文件上吃过两次亏）。所以图形全部用 QPainter 现画，并按 devicePixelRatio 放大绘制：

* `brand_pixmap` / `tray_pixmap` —— 蓝色圆角方牌 + 盾牌里的暂停条 + 状态角标，
  **托盘图标与面板共用同一套画法**（以前托盘是个圆环，两处像两个产品）
* `glyph_pixmap` —— 线性小图标（暂停/刷新/波形/换边/盾牌），统一线宽与圆头
* `StatusDot` —— 状态点，RUNNING 时带一圈扩散脉冲（只在"运行中且可见"时跑定时器）
* `Switch` —— 开关式 QCheckBox（**继承并只接管绘制**，`isChecked/setChecked/toggled`
  语义原样保留 —— 界面与用例都依赖它）

#### 两个性能相关的视觉决策

1. **投影不用 `QGraphicsDropShadowEffect`**。图形效果会让整张卡片（含所有子控件）
   每帧离屏渲染再模糊一遍，而状态点的脉冲是 16fps 的 —— 等于每秒做 16 次 22px 高斯
   模糊。改成"由内向外渐隐的一圈描边"画进**缓存位图**，只在面板尺寸变化时重画。
2. **所有会触发重排的动作都先判"值变了吗"**。`setStyleSheet` / `setPixmap` /
   `setVisible` 都会引发 polish + repaint，而 `apply_status` 每轮 tick 都跑。

#### 排版事故：尾部伸缩项吞掉高度

第一版重构后，`meta` 行结束在 y=146，主按钮却从 y=184 开始 —— 中间 38px 全被
布局尾部的 `addStretch(1)` 吃掉，看上去像"界面没画完"。面板高度本来就是按内容
贴合的（`_refit` 用 sizeHint），这个弹簧没有任何存在意义，删掉即可。
回归用例 `t_ui_design` 会把「底部空档 ≤ 12px」钉住。

#### 其它细节

* 禁用态的主按钮改成**中性灰 + 摘掉图标**：原先"淡蓝底 + 白字 + 白色图标"
  对比度最低，看起来像没画完（白色图标在浅底上等于糊了一块白）。
* 强提醒出现时**自动收起底部工具行与元信息**，把空间让给提示本身 ——
  用户被拦下那一刻要读的是"为什么被拦"，不是诊断入口和换边按钮。
* 4 个状态各留一张截图与一张总览图：`tests/out/ui_panel.png`、
  `ui_panel_notice.png`、`ui_design_sheet.png`。

### 4.4.5 状态确认节拍压到 0.5~1.0s（2026-10-01，用户要求）

用户要求「大概 0.5~1 秒确认一次状态」。表面只是改一个数字，实际有两个前提必须先想清楚。

#### 前提一：tick 节拍是轮询的**上限**

`_poll_state` 只在 tick 里被调用，而 tick 周期由 `ui.refresh_ms` 决定。
上一轮为了省 CPU 曾把 tick 放宽到 1000ms —— 那种设置下**即使把 poll_ms 改成 500
也跑不出 0.5s 的节拍**（每 1 秒才轮到一次）。所以两个值必须一起动：

| 项 | 旧 | 新 | 说明 |
| --- | --- | --- | --- |
| `ui.refresh_ms`（tick） | 1000ms | **500ms** | 同时刷新死手窗口，须远小于 2500ms |
| `duration.poll_ms`（基准） | 1000ms | **500ms** | |
| `POLL_FACTOR` | 1.0 / 1.5 / **3.0** | 1.0 / 1.4 / **2.0** | 倍率上限定在 2.0，否则最慢那档出界 |

出厂默认下的有效节拍：**RUNNING 0.5s · UNKNOWN 0.7s · PAUSED 1.0s** —— 三态都落在用户要的区间里。
回归用例 `t_perf_contract` 里有一条直接按出厂默认算这三个值并断言 0.5≤v≤1.0，
以后谁调 `POLL_FACTOR` 都会当场知道有没有出界。

#### 前提二：贵的那一步不按轮询间隔来

调快轮询最容易踩的坑是「顺带把 CPU 也调高了」。这个项目不会，因为最贵的一步被单独门控：

| 步骤 | 真机耗时 | 由谁门控 | 轮询变快会不会变多 |
| --- | --- | --- | --- |
| 全量枚举控件树 | ~657ms | `ui_automation.CACHE_TTL` | **不会** |
| OCR 整窗识别 | ~1.3s | `ocr_mode=auto`（UIA 定论即跳过）+ 60s 几何刷新 | 不会 |
| 重读 1~2 个控件的 Name | **0.3ms** | 每轮都做 | 会（但可忽略） |

也就是说：1000ms → 500ms 只多了每秒一次的微秒级读取。**顺带把 `CACHE_TTL` 从 3.0s
放宽到 5.0s** —— 轮询变快后，全量枚举的频次反而更低（约 1 次/5s），后台占用比改动前还轻。

> 为什么放宽 TTL 不会让状态变迟钝：**状态变化不靠 TTL 发现**。缓存元素的名字一变就被读到，
> 元素一失效立刻退回全量扫描 —— 检测延迟只取决于轮询间隔（0.5s）。
> TTL 只决定"多久整体核对一遍"。而放行 ✕ 之前那次全量扫描是 `_verify` 里的**独立**地面真相，
> 不受 TTL 影响。

#### 界面同步

面板右上角原先显示「0s 前确认」，节拍压到 0.5s 后这个数字既没信息量又显得卡 ——
一秒以内统一改说「刚刚确认」，超过一秒才报秒数；悬停提示里的「每 x.x 秒重新识别一次」
取的是**实时有效节拍**（status 里的 `poll_ms`），不是配置基准值（自适应轮询下两者本来就不同）。

## 9. 诊断与校准工具

### 9.1 Leigod UI Inspector

```bat
dist\LeigodGuard\LeigodGuardCUI.exe --inspector
```

输出：雷神 PID / HWND / 窗口标题 / 类名 / 进程路径 / WindowRect / 宽 / 高 / DPI（含缩放比）/ 显示器 / 托盘态；控件树；"开启时长 / 暂停时长"的 Name / ControlType / AutomationId / BoundingRectangle / 是否支持 Invoke；截图 `leigod_full.png`、`duration_region.png`；OCR 的 `recognized_text` / `confidence` / `bounding_box`；最终 `DurationState`。结论为 UNKNOWN 时退出码为 2。

**雷神更新后认不出按钮时，第一步就是重新跑它。**

### 9.2 坐标校准

```bat
dist\LeigodGuard\LeigodGuardCUI.exe --calibrate --mode auto
```

校准结果包含窗口身份（HWND/类名/PID/版本/宽高/DPI）、相对坐标（`ratio` 与 `pos`）、目标区域元数据——**不含绝对屏幕坐标**。

并且：**校准完成后会立即执行一次真实点击测试**（RUNNING → 点击 → 重新识别 → 是否变 PAUSED）。没有变成 PAUSED 就是 `Calibration FAILED`，**绝不会显示 SUCCESS，也不会覆盖原有可用校准**。

前置拒绝：状态 UNKNOWN（请先跑 `--inspector` 排障）或已 PAUSED（请先在雷神里点一次「开启时长」）时，校准会以 `CANNOT_RUN` 退出且**零点击**。

### 9.3 OCR 按钮定位（真机主用路径）与离线验证

真机实测：UIA 对雷神主窗口枚举到 **0 个控件**（Electron 主窗口未暴露 UIA 树），因此 §9.2 的坐标校准与 UIA 调用在真机上**都不一定可用**。**暂停按钮的定位因此改为「用 OCR 识别到的按钮文字框实时现算」**——它天然满足规格书「不保存绝对屏幕坐标」的要求，也省掉了真机上无法完成的人工校准。

换算分三步（截图数组像素 → 裁剪区像素 → 窗口坐标系 → 屏幕坐标），并带两道拒绝：文字框过宽（> 窗口宽 26%，说明整行被合并成一个框）或置信度低于 0.5 时**放弃定位**，绝不退化成「点窗口中心」。

用真实截图离线验证（不需要雷神在跑）：

```bat
python tests\verify_ocr_button_locate.py real_state\leigod_full.png
```

它会把识别到的文字框、换算后的屏幕矩形、以及**画了框的存档图**写到 `tests/out/ocr_locate/`，便于肉眼确认框是否正好套住真按钮。

## 10. 已知限制与残留风险

1. **必须以管理员身份运行（实测确认是硬性要求，不是建议）。** 实测读取 PE 内嵌清单：`leigod.exe` 与 `leigod_launcher.exe` 都是 `requestedExecutionLevel level="requireAdministrator"`——雷神**永远**以高完整性级别运行。因此本程序若未提权，Windows 的 UIPI 会让**两条关闭保护链路双双静默失效**：
   - v2 主路径：低层鼠标钩子（`WH_MOUSE_LL`）能装，但跨进程核查与后续合成点击会被 UIPI 拦下；
   - 旧机制：`EnableMenuItem(SC_CLOSE)` 被拒绝，表现为「✕ 看起来灰了，其实还能点」。
   对应措施：
   - 打包产物已在清单中声明 `requireAdministrator`，启动时弹一次 UAC；
   - 程序另保留运行时权限自检（`leigod/close_protection.py::is_elevated()`）；
   - **当保护未能真正生效时，面板会如实显示原因（如「关闭保护：未能生效（权限不足）」），绝不会显示成「待命中」来制造虚假的安全感**；
   - 用源码运行时（`python main.py`）不会自动提权，需从管理员命令行启动。判定方法：`--check` 看「权限自检」。
2. **绕不过的关闭途径（设计上就绕不过，非缺陷）：** 任务管理器结束进程、任务栏右键关闭、以及**程序化投递的 `PostMessage(SC_CLOSE)` / `WM_CLOSE`** 不经过用户输入链路，低层鼠标钩子与系统菜单状态均约束不到。本工具拦的是**真实用户操作**（点 ✕ / Alt+F4）。另外，v2 的吞点采用**死手开关**：消费端超时未刷新时钩子自动停止吞点（局部 fail-open）——宁可漏保一次，也不把用户锁死。
3. **需要真实雷神在其前台时截图 OCR 才准。** 屏幕抓取要求雷神在前台（避免截到被遮挡画面）；`PrintWindow` 抓 GPU 渲染窗口在目标提权时会得到黑图，程序会做图像有效性校验并判 UNKNOWN。
4. **客户端更新可能改动 UI。** 按钮文案、位置、窗口类名一变，就可能识别不到——此时一律 UNKNOWN（**不会盲点**），需要重新跑 UI Inspector 适配。
5. **本机合成鼠标输入的可用性不稳定（仅影响自动化测试，不影响真机功能）。** 同一台机器上，合成输入**时灵时不灵**：`tests/out/synthetic_input_report.txt` 记录它被 UIPI 拦截（`SetCursorPos` 返回 False、`mouse_event` 无效）；但也观测到它可用——`mouse_event` 能触发结构仿真靶机的完整关闭链（`mock_nclbuttondown → mock_syscommand → mock_wm_close → mock_destroyed`），v2 的 `test_close_guard.py` 正是用**真实点击 + 真实低层钩子**跑通的。因此：① 不把合成输入当作永恒前提，测试里凡依赖它的地方都保留替代路径（坐标仍**真实计算**、命中测试走**真实 `WM_NCHITTEST`**，仅替代内核派发那一段）；② v2 闭环用例在可用时优先走真实路径，以便真机化程度尽可能高。**关键：这条限制只影响测试手法，不影响产品行为——真机上用户点击本来就是真实输入。**
6. **失败安全意味着"雷神可能暂时关不了"。** 这是刻意的取舍：当状态无法确认时，程序会选择保护你的总时长，而不是顺从你的关闭动作。
7. **雷神弹出自己的确认框期间，状态读不到（真机实测）。** 重放关闭点击后雷神会弹「最小化到托盘 / 退出加速器」那个框，它是**在主窗口内绘制的模态层**：此时 UI Automation 能枚举到的控件从 ~476 个掉到 5 个，OCR 也会报「截屏区域被其它窗口遮挡」。于是状态恒为 UNKNOWN —— 这不是识别故障，是**被挡住了**。程序对此的处理：① **判定不变**，仍按 §六 当作 UNKNOWN，绝不当 PAUSED；② 在诊断信息里注明「控件数偏少，若雷神正弹着确认框/模态层则属正常遮挡」，而不是只丢一句"状态未知"；③ 那个框**由你自己选**（我们不替你点），时长此前已暂停，选哪个都不会继续消耗。

> ✅ **真机已跑通（v11.3.2.9，实测 5 轮）**：主路径五环全部取得证据 ——
> `swallowed=1`（✕ 被吞）→ 暂停回调 `success=True` → 复核为 PAUSED →
> `replayed=1` 且事件 `close_released`（「已重新检测到 PAUSED，放行关闭」）→
> `confirm_seen=1`（OCR 命中「最小化到托盘」→ 证明重放**真的送达了雷神**，
> 而不只是 `SendInput` 返回成功；§三十三 不许拿"发出去了"冒充"送达了"）。
>
> 第 5 轮另记录了一个真实现象：确认框弹出期间，雷神的 UIA 控件树从 ~476 个掉到 5 个、
> OCR 报「截屏区域被其它窗口遮挡」→ **状态复核不了**，判定为
> `protected_state_unreadable`（主路径成立，但**不声称已暂停**，按 §六 UNKNOWN 不当 PAUSED）。

结论只可能来自证据：`protected`（吞点→暂停复核→重放→**确认框也被监测到**，完整证实）／
`protected_state_unreadable`（主路径已证实，但收尾复核不了 —— 确认框遮挡导致状态读不到，
**按 §六 不声称已暂停**，请你目视确认）／
`protected_confirm_unverified`（主路径通了，但没拿到"雷神真的收到点击"的独立证据）／
`swallowed_no_replay`（吞了但没重放 = Fail Safe 按设计生效）／`not_swallowed`（收到但按判据放行）／
`no_click_seen`（钩子没收到 = 多半没提权）／`cannot_run`（前提不成立，已中止、未消耗额外时长）／
`inconclusive`。**推不出结论就报 `inconclusive`，不会编一个"成功"出来**（§三十三）。

> ⚠️ **为什么废弃「真人点两次 ✕」的人工版**（`verify_close_loop_real.py` 保留但不再作为主路径）：
> 那套流程的三个要求互相打架，而且**违背了本项目的目的**——
> ① 雷神必须恒在前台（否则 OCR 拿不到画面），但提示只打在控制台，
>    用户被迫在两个窗口间来回切，**而切换本身就在破坏前提**；
> ② 为了测「拦截」必须先让雷神进入计时中，也就是**先消耗用户的总时长**，
>    而这个工具存在的唯一理由就是防止总时长被无意义消耗 —— 为了验证去制造它要防的损失；
> ③ 阶段 2（第二次点 ✕）只为判定确认框形态，产品价值极低，却要用户再配合一次。
> 自动版把这三件事全部收进脚本，人力成本降为零；
> 「处于计时中」的时间也被严格记账（`running_seconds`，默认不超过 90s），**收尾必定恢复暂停**。

> ⚠️ **「当前必须先 PAUSED」这条要求曾经写反过**，代价是一整轮无效人工验证，务必记牢：
> 钩子侧 4 条联合判据里有一条是「状态 ∈ {RUNNING, UNKNOWN}」。**PAUSED 时按设计不拦截**——
> 那时没有时长在消耗，没有需要保护的东西，硬拦反而挡了用户的正常操作。
> 于是「要求先 PAUSED 以免损失时长」= **永远测不到吞点**，逻辑自相矛盾。
> 现在脚本要求的是**计时中**，且这段时间是脚本自己控制、自己记账、收尾必定恢复。

> **如果它一直提示"请点开启时长"，通常不是雷神没切换，而是读不到状态**——
> 最常见的原因是**雷神不在最前面**（截屏护栏拒绝截屏，于是 UNKNOWN）。
> 正确做法：把雷神窗口点回最前面并停一下，**不要切到控制台或其他窗口**再看。
> 现在脚本会区分提示：是"已暂停（请点开启时长）"还是"雷神不在前台（请点回前台）"，
> 不会再用同一句含糊的提示。

> ⏳ **「开启时长」→「暂停时长」之间存在 1~2 秒过渡态**（真机实测）：
> 点下「开启时长」后按钮**不会立刻变红变字**，而是先变成**灰底、字体变浅、文字仍为「开启时长」**，
> 约 1~2 秒后才渲染成红色的「暂停时长」。
> 这段窗口内 UIA 与 OCR 都可能读到**互相矛盾**的证据（例如 UIA 同时枚举到
> 「暂停时长」×1 与「开启时长」×20 —— 后者多为页面其它位置/隐藏节点上的同名控件），
> 于是状态被判为 `UNKNOWN`（冲突），这不是故障。
> 对策：点完「开启时长」**停 1~2 秒再看**；脚本侧已做两件事——
> ① UIA 候选按 `detection.topbar_crop` **顶栏区域过滤**（与 OCR 同一套裁剪参数）并优先取 `is_offscreen=False` 的控件，
> 把"页面其它位置的同名控件"剔除；② 冲突提示里明确写出"刚点过开启时长 → 过渡态，等 1~2 秒"。

提权后 UIA 能枚举到控件（实测 476 个，未提权时恒为 0 —— **别拿未提权的数据下结论**），

## 13. 开发过程中发现并修复的缺陷

> "不许假装成功"是本项目的最高开发纪律。以下 5 类缺陷是**新写的测试自己发现的**，而不是靠人工以为没问题（另有 3 条真机阶段暴露的问题见 §13.1、5 条层级 3 接线后暴露的消费端阻塞/滞后缺陷见 §13.2，合计 13 条）：

1. **日志脱敏顺序错误**：`Authorization: Bearer eyJ...` 只把 `Bearer` 打码，令牌裸露。修复：把 `Bearer` / `Cookie` 正则挪到通用 `key:value` 正则**之前**。
2. **OCR 冲突判定被顺序掩盖**：`"暂停时长 开启时长"` 并存时被判为 PAUSED。修复：把冲突判定提到最前。
3. **OCR 漏"开肩"误识别**：`"开肩时长"` 无法判定。修复：补充关键词。
4. **`crop_relative` 越界**：`{"left":1.0,"right":0.0}` 静默返回空图。修复：坐标夹紧，至少保证 1×1 像素。
5. **单实例句柄泄漏**：第二个实例拿到互斥体后不关句柄，内核对象永生，后续实例永远被拒。修复：`ERROR_ALREADY_EXISTS` 分支立即 `CloseHandle`。

此外还修掉了一处**打包后才会暴露**的假阳性：UIA 可用性探测只判断 `import` 成功，没验证客户端 DLL 是否真的加载（打包漏收 DLL 时会"假可用"，导致第一优先级静默失效）。现已改为真实校验 DLL，`--check` 会显示 `UIA 可用（DLL 已加载：UIAutomationClient_VC140_X64）`。

### 13.1 真机试跑后又抓到的三个问题

第一次真正启动雷神时，又暴露出只有在真机上才会发生的问题：

6. **`start_leigod` 的 CreateProcess 标志非法（已修复）。** 报 `[WinError 87] 参数错误`——根因是 `DETACHED_PROCESS` 与 `CREATE_NEW_CONSOLE` 在 Windows 上**互斥**，同时传会被直接拒绝。已抽出 `SPAWN_FLAGS = DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` 统一引用。
   **为什么之前没测出来**：`case_ensure_with_mock` 走的是"雷神已在运行"的早退分支，`case_ensure_missing_exe` 在文件存在性检查处就返回了——**两条用例都没真正执行到 `Popen`，启动路径是测试盲区**。教训是：只覆盖"对象已就绪"和"对象缺失"，等于没测"正常创建"这条主路径。已新增 `case_spawn_path` 回归测试（断言标志互斥 + 用该标志真实拉起进程 + 校验启动处确实引用该常量）。

7. **拦截失败会被显示成"一切正常"（已修复）。** 当 UIPI 静默拒绝禁用系统菜单时，旧写法会落到 `else` 分支显示「关闭保护：待命中」——而实际是"保护根本没在工作"。这违反了本项目"不许假装成功"的最高纪律。已抽出 `ui/theme.py::protection_line()`，在"本该拦截却没拦住"时明确显示权限不足与解决办法，并配了 7 项单元测试盯住这条分支。

8. **输入层钩子的回调异常被完全静默吞掉（v2 开发中自查发现并修复）。** 关闭保护 v2 的消费端 worker 在 `logger=None` 时，`except` 分支**没有任何落点**——异常既不记录也不上报。真实后果极具迷惑性：钩子侧统计 `swallowed=1`（看起来吞点成功），但暂停与重放**永不发生**，用户点了 ✕ 却没有任何反应，且**无任何日志**。触发它的正是一个类型用错（`threading.Event` 当作 `Lock` 用，`acquire()` 直接抛 `AttributeError`）。
   **修复**：① `_busy` 改为 `threading.Lock()`；② `_run` 的 `except` **无条件**写入 `self.errors` 并累加 `stats["handled"]`，由 `status()` 与面板状态（`input_layer` 块）对外暴露。
   **教训**：低层钩子场景下「吞下去了」与「处理成功了」是两个必须分开统计的事实——只报前者就会制造"保护生效"的假象。这与第 7 条同源，都是"不许假装成功"的具体化。

### 13.2 层级 3 接线后暴露的一类新缺陷：**消费端 tick 被慢操作阻塞**

层级 3（确认框监测）接线完成后，`test_e2e_mock` 出现 13 项 FAIL，现象是**注入的关闭意图已验证入队（队列长度 1），但引擎毫无反应**（`_consume_close_intents` 调用次数长期为 0，`CLOSE_REQUESTED=0`）。用 4 个只做单一变量的临时探针逐层剥离，得到 4 个**互相独立**的根因——它们共同构成一类新的失败模式：**引擎主循环的 tick 同时承担三件不可被拖慢的事**（消费关闭意图、刷新死手武装窗口、维持界面节拍），任何一件被慢操作阻塞都会引发**静默**的功能退化。

9. **整窗 OCR 跑在消费端主循环里（P0，关闭保护整体失灵）。** 层级 3 的 `poll()` 内部直接调 `_scan_ocr()`，单次 300ms~1.3s。tick 被拖长后 ① `_consume_close_intents` 迟迟得不到执行，关闭意图超过新鲜度上限被**按设计**丢弃；② 死手开关窗口被顶穿，吞点周期性自行解锁。
   **修复**：`ConfirmWatch` 增加**独立 OCR 扫描线程**，`poll()` 退化为 O(1) 的「取结果」操作（`deque` + 锁），扫描用 `Event.wait` 限频、异常只累加 `stats["errors"]` 绝不让线程死掉。**契约**：`poll()` 的总耗时必须与 OCR 成本解耦——已写成回归用例（5 次 `poll()` 总耗时 < 0.15s，而单次 OCR 被故意桩成 0.4s）。
10. **关闭意图的消费排在慢步骤之后（顺序缺陷）。** `_tick()` 里 `_poll_state()`（1.3s）排在 `_consume_close_intents()` 前面，用户点下的那一下在队列里白白等过一次 OCR 才被判过期。
    **修复**：把 `_consume_close_intents()` 提到 `_poll_state()` **之前**，并在代码里留下注释说明这个顺序不可调换。
11. **新鲜度上限被写死，卡在实测 tick 的临界点上。** 固定 1.5s 对 1.4s 的 tick 只剩 0.1s 余量。
    **修复**：`_intent_max_age()` 按**实测消费间隔**自适应 = `clamp(2×interval + 0.3, 1500ms, 5000ms)`；同时新增 `intent_stats{accepted,expired,missed}` 与 `last_intent_note`，并在状态里暴露 `max_age_ms` / `interval_ms`。**判据**：`expired` 持续增长就等于「点了 ✕ 没反应」，这条现在能从状态里直接看出来，而不必等用户投诉。
12. **死手窗口被「忙」而非「死」顶穿。** 固定 2.5s 的下限本是防「消费端死了」的，却被一次 1.3s 的 OCR 顶穿，钩子周期性自行解锁 ✕。
    **修复**：`_arm_window()` = `clamp(tick_ewma × 3, 下限 2500ms, 上限 10000ms)`——按实测节拍放宽，但保留上限确保消费端**真死**时最迟 10s 一定停止吞点；`status()` 暴露 `arm_ms` / `tick_ms` / `deadman_ms`。
13. **新决策滞后一轮 tick 才对外可见。** 状态只在每轮 tick 的**末尾**上报，而一轮 tick 含整窗 OCR 要 1.3s 以上。于是「暂停失败」这个刚刚发生的事实，会在状态里迟到一整轮——界面在那期间仍显示上一轮的决策。
    **表现**：注入关闭意图后等待 2 秒读状态，**间歇性**读到 `BLOCK_RUNNING` 而不是 `BLOCK_PAUSE_FAILED`（`test_e2e_mock` 测试 D 偶发 FAIL）。
    **定位手法**：写一个单一变量的临时探针，以 100ms 粒度打印「状态里的决策 / 引擎内部 `last_report.decision` / `_pause_failed` / `sm.state` / 窗口是否被重新绑定」。数据立刻分晓——`last_report` 从第一毫秒就是 `BLOCK_PAUSE_FAILED`，只有状态在滞后，与窗口重绑无关（一开始的怀疑方向是错的）。
    **修复**：`_consume_close_intents()` 返回「本轮是否真的走了一次关闭流程」，`_tick` 在其后**立刻补报一次**状态，不等这一轮走完。回归断言用「滞后 < 1s」做判别（即时 ≈0.05s，滞后一轮 ≥1.3s，相差一个数量级，既稳定又有区分力）。

> **方法论教训**：这四条如果靠"读代码猜测"，大概率只会改到第 9 条。真正有效的手法是把「注入成功但毫无反应」拆成**四个可独立验证的单一变量探针**（入队是否成功 / 消费函数是否被调用 / tick 实际节拍 / 调用栈帧），逐个排除——而不是一次改一堆然后看现象是否消失。第 13 条同样靠这个手法在几分钟内定案。
>
> **通用原则（已固化为契约）**：
> 1. **消费端 tick 里不得出现任何耗时不可控的同步操作。** 慢活必须移到工作线程，tick 只做「读快照 + 纯数值判断 + 取结果」。
> 2. **所有带新鲜度/超时语义的阈值都不能写死**，必须相对实测节拍自适应并设上限。
> 3. **刚产生的决策必须立刻上报**，不能等这一轮 tick 走完——否则用户看到的永远比现实慢一个节拍。
> 4. **测试不要用固定 `sleep` 去赌"状态应该已经追上"**：用一个数量级的差异做判别（即时 vs 滞后一轮），否则用例本身就是个测不稳的探针。

## 15. 核心目标

> **只要用户不再需要雷神消耗总时长，就尽最大可能确保总时长已经暂停。**
>
> **宁可雷神暂时关不了，也不能让用户在不知情的情况下损失几个小时的总时长。**
